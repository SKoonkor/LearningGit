\section{Why a remote?}

So far everything lived on one computer. That is risky (a lost laptop loses the project) and lonely (nobody else can see or add to it). A \textbf{remote} is simply \emph{another copy of the repository, stored somewhere else}, usually on a server that several people can reach. \textbf{GitHub} is the most popular place to keep one.

(For the first part of this lecture and Homework Part~A, the ``server'' will be just a folder on your own computer, a so-called \emph{bare repository}: a repository without a working folder, which is what a server holds. Git treats a folder path exactly like a GitHub address, so everything works the same. The GitHub account, SSH key and publishing steps come after the core ideas and are needed only for Part~B.)

Remember Lecture 0: Git is \emph{distributed}. Your computer holds a complete repository, GitHub holds another complete repository, and a friend's computer holds a third. They are equals in structure; they stay in step because people \emph{send} commits between them.

\section{Copying a repository: \texttt{git clone}}

To get an existing repository, for example a friend's, you \emph{clone} it. On GitHub the green \textbf{Code} button shows the address.

\Needspace{10\baselineskip}
\begin{lstlisting}
$ git clone git@github.com:friend/project.git
Cloning into 'project'...
$ cd project
$ git remote -v
origin  git@github.com:friend/project.git (fetch)
origin  git@github.com:friend/project.git (push)
$ git log --oneline --decorate
4c2511d (HEAD -> main, origin/main, origin/HEAD) Add notes
3db1fe7 Add README
\end{lstlisting}

(The address may be a GitHub address, as here, or just a folder path such as \code{hw6\_server.git}, as in the homework.) One command created a new folder with the \emph{whole history}, set up the remote called \code{origin}, and checked out the main branch. (\code{git clone <address> mydir} picks another folder name.) You do not run \code{git init} first.

\section{Remote-tracking branches: \texttt{origin/main}}

Look at the log above: it shows both \code{main} and \code{origin/main}. The notation is \code{<remote name>/<branch name>}, and they are different things. (\code{origin/HEAD} is the remote's default branch; ignore it.)

\begin{itemize}
  \item \code{main} is \emph{your} branch. It moves when you commit.
  \item \code{origin/main} is a \textbf{remote-tracking branch}: your computer's \emph{memory} of where \code{main} was on \code{origin} the last time you talked to it. You never commit on it; Git moves it only when you push, fetch or pull.
\end{itemize}

\Needspace{9\baselineskip}
\code{git status} reports the comparison in words:

\begin{lstlisting}
$ git status
On branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)

nothing to commit, working tree clean
\end{lstlisting}

\begin{keyidea}
\code{origin/main} is only as fresh as your last contact. \code{git status} never phones GitHub: if a friend has pushed since, it will still say ``up to date'' until you \code{fetch}.
\end{keyidea}

\section{Getting others' work: \texttt{fetch} and \texttt{pull}}

A friend pushes a commit. Your computer does not know yet. \code{git fetch} downloads new commits and moves \code{origin/main}, but \emph{touches neither your branch nor your files}, so it is always safe:

\begin{lstlisting}
$ git fetch
From github.com:friend/project
   4c2511d..322927b  main       -> origin/main
$ git status
On branch main
Your branch is behind 'origin/main' by 1 commit, and can be fast-forwarded.
  (use "git pull" to update your local branch)

nothing to commit, working tree clean
$ git log --oneline main..origin/main        # commits in origin/main that main lacks
322927b Friend update
\end{lstlisting}

``Behind, and can be fast-forwarded'' is the easy case from Lecture 5: your branch has nothing new, so it just slides forward to catch up. \code{git pull} does exactly a fetch followed by a merge, here a fast-forward:

\begin{lstlisting}
$ git pull
Updating 4c2511d..322927b
Fast-forward
 friend.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 friend.txt
\end{lstlisting}

\subsection{When both sides have new commits}

The harder case: while you made a commit locally, your friend pushed one. Now the two copies have \emph{diverged}, exactly like the two branches of Lecture 5. Git protects the shared copy and rejects your push:

\begin{lstlisting}
$ git push
To github.com:friend/project.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'github.com:friend/project.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. This is usually caused by another repository pushing
hint: to the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.
\end{lstlisting}

The cure is the merge you learned in Lecture 5: first bring your friend's commit in, then push. Git 2.33 and newer, however, insist that you \emph{choose} how \code{pull} should combine two diverged branches (if you see no such message, your Git is already configured, so carry on):

\begin{lstlisting}
$ git pull
From github.com:friend/project
   4c2511d..322927b  main       -> origin/main
hint: You have divergent branches and need to specify how to reconcile them.
hint: You can do so by running one of the following commands sometime before
hint: your next pull:
hint:   git config pull.rebase false  # merge
hint:   git config pull.rebase true   # rebase
hint:   git config pull.ff only       # fast-forward only
fatal: Need to specify how to reconcile divergent branches.
\end{lstlisting}

(Some hint lines are left out.) Notice that the fetch part already worked: \code{origin/main} moved. Only the combining step is waiting for your decision. We choose \textbf{merge}, which you know, and say so once for all repositories with \code{--global} (rebase is Lecture 8; the homework sets it for one repository only):

\begin{lstlisting}
$ git config --global pull.rebase false
$ git pull --no-edit              # fetch + merge origin/main (--no-edit skips the message editor)
Merge made by the 'ort' strategy.   (older Git: 'recursive')
 friend.txt | 1 +
 1 file changed, 1 insertion(+)
 create mode 100644 friend.txt
$ git push
To github.com:friend/project.git
   322927b..3bd108e  main -> main
\end{lstlisting}

The same thing, step by step, is \code{git fetch} followed by \code{git merge origin/main}. If the merge ever conflicts, resolve it exactly as in Lecture 5, then commit and push.

\begin{quickfact}
Never use \code{git push --force} to get around a rejection. It overwrites the remote with your version and \emph{deletes your friend's commits} from it. Beginners should treat it as forbidden until Lecture 8.
\end{quickfact}

\section{Branches and the remote}

A new branch exists only on your computer until you push it. Use \code{-u} the first time. It sets the branch's \emph{upstream}: it pairs your local branch with the remote branch of the same name (``set up to track'' in the output below), so afterwards a plain \code{git push} or \code{git pull} knows where to go.

\begin{lstlisting}
$ git switch -c feature
$ git commit -m "Add feature file"       # after creating and adding feature.txt
$ git push -u origin feature
To github.com:friend/project.git
 * [new branch]      feature -> feature
branch 'feature' set up to track 'origin/feature'.
$ git branch -vv
* feature d74b2c7 [origin/feature] Add feature file
  main    3bd108e [origin/main] Merge branch 'main' of github.com:friend/project
$ git branch -r
  origin/HEAD -> origin/main
  origin/feature
  origin/main
\end{lstlisting}

\code{git branch -vv} shows which remote branch each local branch tracks; \code{git branch -r} lists the remote-tracking branches. To delete a branch on the remote once it is merged: \code{git push origin --delete feature}. (Git removes your own \code{origin/feature} label at once. If someone else deletes a branch on GitHub, for example with the website's ``Delete branch'' button, \code{git fetch --prune} removes the stale label on your side.)

\section{Setting up GitHub}\label{sec:github-setup}

Do these once. They take about ten minutes. \textbf{Homework Part~A does not need them; they are needed for Part~B}, so you can also do Part~A first.

\subsection{Account and your private email address}

Create a free account at \url{https://github.com} and turn on two-factor authentication (Settings, ``Password and authentication''). Choose your user name carefully: it appears in every repository address.

In Lecture 1 you put your email address into \code{git config}, and in Lecture 3 you saw that every commit carries it. Commits pushed to GitHub show that address \emph{publicly}. GitHub offers a private ``no-reply'' address that works instead:

\begin{enumerate}
  \item In GitHub \textbf{Settings $\rightarrow$ Emails}, tick \emph{Keep my email addresses private}. The option below it, \emph{Block command line pushes that expose my email}, rejects any push containing a commit with your real address, \emph{including old ones}. Your commits from Lectures 1--5 have it, so leave that second option unticked for now, or use a brand-new repository for Part~B (as the homework does).
  \item The same page shows your no-reply address: a number, a plus sign, your user name, and \code{@users.noreply.github.com}. Copy it from there rather than typing it.
  \item Tell Git to use it for future commits:
\end{enumerate}

\begin{lstlisting}
$ git config --global user.email "12345678+yourname@users.noreply.github.com"
\end{lstlisting}

Commits you have \emph{already} made (such as those of Lectures 1--5) keep the old address; the setting changes only new commits. Rewriting old history to change them is possible but out of scope here, so do not worry about it. Check the setting any time with \code{git config --global user.email}.

\subsection{Authentication: proving who you are}

To \code{push} you must prove that the repository is yours. GitHub no longer accepts your account password for this. There are two ways:

\begin{itemize}
  \item \textbf{HTTPS with a token.} Repository addresses start with \code{https://}, and you paste a long, secret \emph{personal access token} where a password would go.
  \item \textbf{SSH with a key} (recommended). Repository addresses look like \code{git@github.com:}\allowbreak\code{yourname/repo.git}. You create a pair of key files once; afterwards you do not paste a token on every push.
\end{itemize}

An \textbf{SSH key} is a pair of files, like a padlock and its key. The \emph{public} half is the padlock: you may give it to anyone, and you put it on GitHub. The \emph{private} half is the key that opens it: it never leaves your computer.

\begin{figure}[H]
\centering
\begin{tikzpicture}[
  box/.style={draw,rounded corners,minimum width=4.6cm,minimum height=2.0cm,align=center,font=\small}]
  \node[box,fill=blue!8] (a) at (0,0) {\textbf{Your computer}\\[2pt]\code{id\_ed25519}\\private key: \textbf{secret}};
  \node[box,fill=orange!12] (b) at (10.6,0) {\textbf{GitHub}\\[2pt]your public key\\(copy of \code{id\_ed25519.pub})};
  \draw[->,thick,>=Stealth] ([yshift=4mm]a.east) -- node[above,font=\scriptsize] {upload the public half (once)} ([yshift=4mm]b.west);
  \draw[<->,thick,>=Stealth,dashed] ([yshift=-4mm]a.east) -- node[below,font=\scriptsize] {proves you hold the private half} ([yshift=-4mm]b.west);
\end{tikzpicture}
\caption{A key pair. Only the public half is ever uploaded.}
\label{fig:keys}
\end{figure}

\textbf{Create the key} (in a terminal; in Git Bash on Windows). Use your own email address as the label, and a passphrase when asked:

\begin{lstlisting}
$ ssh-keygen -t ed25519 -C "you@example.com"
Enter file in which to save the key (/Users/you/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
\end{lstlisting}

At the first question just press Enter. At the passphrase question type a passphrase (a password for the key file); \emph{no characters appear while you type}, which is normal. Type it again to confirm. (If it says the key already exists, answer \code{n} and reuse the existing key.)

This creates two files in the hidden folder \code{\textasciitilde{}/.ssh/}: \code{id\_ed25519} (private) and \code{id\_ed25519.pub} (public). Print the public one and copy the whole line:

\begin{lstlisting}
$ cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3Nza...(long)... you@example.com
\end{lstlisting}

On GitHub open \textbf{Settings $\rightarrow$ SSH and GPG keys $\rightarrow$ New SSH key}, give it a title (for example ``my laptop''), paste the line, and save. Then test the connection:

\begin{lstlisting}
$ ssh -T git@github.com
Hi yourname! You've successfully authenticated, but GitHub does not provide shell access.
\end{lstlisting}

That message is success: GitHub knows you, and (as it says) does not give you a command line on its servers. The first time, SSH asks whether to trust the server; compare the fingerprint it prints with the one on GitHub's documentation page ``GitHub's SSH key fingerprints'', then answer \code{yes}.

If you set a passphrase, your computer may ask for it on every push. Let it remember the passphrase for this session with \code{ssh-add \textasciitilde{}/.ssh/id\_ed25519} (on macOS: \code{ssh-add --apple-use-keychain \textasciitilde{}/.ssh/id\_ed25519}). On Windows, Git Bash shows your home folder as \code{/c/Users/yourname}, and you may first need \code{eval "\$(ssh-agent -s)"} to start the agent.

\begin{pitfall}
\textbf{If the test fails.} \code{Permission denied (publickey)} means GitHub does not know your key: re-copy the \emph{whole} line of the \code{.pub} file into GitHub (not the private file), and check that you added it to your own account. \code{Could not resolve hostname} means no internet connection.
\end{pitfall}

\begin{pitfall}
Never share, e-mail or upload \code{id\_ed25519} (the private key; the file ending in \code{.pub} is the safe one), and never commit a \code{.ssh} folder. If you suspect it leaked, delete the key on GitHub and create a new pair. The passphrase protects the file if your laptop is stolen.
\end{pitfall}

\begin{quickfact}
If you prefer HTTPS: create a \emph{classic} token under Settings $\rightarrow$ Developer settings $\rightarrow$ Personal access tokens, tick only the scope \emph{repo}, and paste it when Git asks for a password. In Part~B copy the HTTPS address instead of the SSH one; the checker accepts both. Your operating system can remember it (the \emph{credential helper}). Everything else in this lecture is identical: only the address style differs.
\end{quickfact}

\section{Putting a local repository on GitHub}

You already have a local repository. To share it:

\begin{enumerate}
  \item On GitHub click \textbf{New repository}. Give it a name and choose public or private.
  \item \textbf{Do not} tick ``Add a README'', ``.gitignore'' or ``license''. Those would create a first commit on GitHub that your local history does not contain, and the two histories would not fit together. You want an \emph{empty} repository.
  \item GitHub now shows its quick-setup page with the repository's address. Copy the SSH address, and read the warning below before you copy any snippet.
\end{enumerate}

\begin{pitfall}
If you ticked ``Block command line pushes that expose my email'' (Section~\ref{sec:github-setup}) and any commit you push carries your real address, the push is refused with an error starting \code{GH007}. Commits that already exist cannot be changed: untick the option, or push only commits made \emph{after} you set the no-reply address with \code{git config user.email} (without \code{--global} it applies to one repository). For a single latest commit, \code{git commit --amend --reset-author} re-stamps it with your current setting.
\end{pitfall}

\begin{pitfall}
That page offers two snippets, and the wrong one can do damage. The \emph{first} (``create a new repository on the command line'') starts with \code{echo "\# name" >> README.md} and \code{git init}. It is for a \emph{brand-new, empty folder}. Run inside an existing project, it appends a stray line to your README. You want the \emph{second} (``push an existing repository''), which has three lines. One of them, \code{git branch -M main}, \emph{renames the branch you are currently on} to \code{main}, so check with \code{git branch --show-current} that you are on the branch you mean. (\code{-M} also \emph{overwrites} an existing branch of that name: run on \code{feature} while \code{main} exists, it replaces \code{main}.)
\end{pitfall}

The three commands, run inside your existing repository:

\begin{lstlisting}
$ git remote add origin git@github.com:yourname/hello-github.git
$ git remote -v
origin  git@github.com:yourname/hello-github.git (fetch)
origin  git@github.com:yourname/hello-github.git (push)
$ git push -u origin main
To github.com:yourname/hello-github.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
\end{lstlisting}

(Real output also shows progress lines such as \code{Counting objects}, left out here.) Line by line:
\begin{itemize}
  \item \code{git remote add origin <address>} gives the remote a short name. \code{origin} is the conventional name for ``the place I got this from or share it with''; it is only a label.
  \item \code{git remote -v} lists your remotes. To change an address later: \code{git remote set-url origin <new-address>}.
  \item \code{git push -u origin main} sends the commits of the branch \code{main} to \code{origin}. The \code{-u} (``upstream'') makes your \code{main} \emph{remember} that it belongs with \code{origin/main}, so that afterwards a plain \code{git push} or \code{git pull} is enough.
\end{itemize}

\section{What GitHub adds}

The website shows your repository: files, the commit list, branches, and the \code{README.md} rendered as a front page. A README is written in \textbf{Markdown}, a plain-text format where \code{\# Title} is a heading, \code{**bold**} is \textbf{bold}, \code{- item} starts a list, and backticks make \code{code}. You can also edit a file in the browser (the pencil icon) and ``commit changes'' there. That creates a \emph{commit on GitHub}, which your local copy does not have until you \code{git pull}.

\begin{pitfall}
Everything you push is as visible as the repository: anyone can read a \emph{public} repository, and history keeps every old version. Never push passwords, keys or tokens (Lecture 2), even in a file you later delete.
\end{pitfall}

\section{Summary}

\begin{itemize}
  \item A remote is another full copy of the repository; \code{origin} is the usual name for the one you share with. \code{origin/main} is your memory of where \code{main} was on it.
  \item Set up GitHub with a private no-reply email and an SSH key (public half uploaded, private half secret).
  \item \code{git remote add}, \code{git push -u origin main} publish a local repo (create it \emph{empty} on GitHub); \code{git clone} copies one.
  \item \code{fetch} downloads safely; \code{pull} is fetch plus merge. If both sides have new commits, pull (merge) first, then push. Never force-push.
\end{itemize}

\textbf{Further reading:} \emph{Pro Git}, Chapters 2.5 and 3.5; GitHub Docs, ``Connecting to GitHub with SSH''.
